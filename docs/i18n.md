# 国际化

Pi Web 的界面使用一个很小的内置 i18n 层。它刻意留在应用内部，而不是引入另一个运行时依赖，这样界面可以支持更多语言，同时不让服务端、API 响应或 pi 自身的输出绑定到某一种语言。

## 当前语言

内置语言包为：

- `en` —— 英文
- `zh-CN` —— 简体中文
- `zh-TW` —— 繁体中文

初始语言根据浏览器推断，用户可以在顶栏的语言控件里切换。所选语言保存在 `localStorage` 的 `pi-locale` 下。

繁体中文的浏览器语言（`zh-TW`、`zh-HK`、`zh-MO` 及 `zh-Hant` 变体）解析为 `zh-TW`；裸 `zh`、简体区域与 `zh-Hans` 变体解析为 `zh-CN`。

## 在组件里使用翻译

客户端组件应当通过 `useI18n` 获取翻译函数：

```tsx
import { useI18n } from "@/hooks/useI18n";

export function ExampleButton() {
  const { t } = useI18n();

  return <button aria-label={t("example.open")}>{t("example.open")}</button>;
}
```

组件必须渲染在 `I18nProvider` 之下；应用根节点已在 `app/page.tsx` 提供它。

运行时才确定的值请使用参数，不要拼接翻译片段：

```tsx
<span>{t("session.messageCount", { count: messageCount })}</span>
```

对应的文案可以使用 `{count}`：

```ts
"session.messageCount": "{count} messages"
```

这样句子结构由各语言包自己决定。

## 新增一种语言

### 1. 创建语言包文件

在 `lib/i18n/messages/` 下新增文件，使用 BCP 47 风格的标识符。例如日语包为 `lib/i18n/messages/ja.ts`：

```ts
import type { LocalePlugin } from "../types";

/** Pi Web 日语语言包。 */
export const jaLocale: LocalePlugin = {
  id: "ja",
  label: "日本語",
  messages: {
    "common.language": "言語",
    // 其余共享 key 补充在这里。
  },
};
```

消息 key 必须保持稳定且与语言无关。新建语言包时请从 `lib/i18n/messages/en.ts` 复制完整 key 集合。缺失的 key 会回退到英文，但面向用户的语言仍应以完整语言包为目标。

### 2. 注册语言包

在 `lib/i18n/registry.ts` 中导入并加入 `localePlugins`：

```ts
import { jaLocale } from "./messages/ja";

const localePlugins: LocalePlugin[] = [enLocale, zhCNLocale, zhTWLocale, jaLocale];
```

`label` 会显示在语言选择器里；`getSupportedLocales()` 会自动把该列表里的语言包暴露给界面。

### 3. 按需更新语言相关类型

内置的 `Locale` 类型目前为编译期安全列出了 `en`、`zh-CN`、`zh-TW`。新增内置语言时，请更新 `lib/i18n/types.ts` 中的联合类型，并更新任何有意列出内置标识符的语言校验逻辑。

### 4. 补测试

浏览器语言识别或语言列表变化时扩展 `lib/i18n/registry.test.mjs`；插值或本地化格式化变化时扩展 `lib/i18n/format.test.mjs`。新语言至少应验证其注册 id 与一条有代表性的翻译。

## 新增或修改界面文案

1. 在 `lib/i18n/messages/` 的每个内置语言包里添加稳定的 key（`en.ts`、`zh-CN.ts`、`zh-TW.ts`）。
2. 把 key 放在功能命名空间下，例如 `chat.*`、`files.*`、`settings.*`、`common.*`。
3. 可见文本、`title`、`aria-label`、`placeholder` 都使用 `t("namespace.key")`。
4. 计数、名称、路径等运行时值使用插值。
5. 产品名、模型名、提供方名、命令、文件路径、用户内容、工具输出以及服务端返回的错误详情保持原样。
6. 不要通过匹配英文文案来翻译 API 错误，只翻译它周围的本界面兜底文案。

翻译时，如果译成中文会让界面难以对应回命令、配置字段或 pi 文档，就保留既有技术术语的英文，包括 `Agent`、`API Key`、`Provider`、`Token`、`worktree`、`Diff`、`CWD`、`Shell`、`Git`、`HEAD`、`OAuth`、`Mermaid`，并保持它们惯用的大小写；把它们周围的动作与状态文案翻译成中文。有明确中文说法的常用概念（模型、插件、技能、提示词、上下文、缓存等）可以本地化。

例如：

```ts
// en.ts
"files.uploadedCount": "{count} uploaded"

// zh-CN.ts
"files.uploadedCount": "已上传 {count} 个文件"

// zh-TW.ts
"files.uploadedCount": "已上傳 {count} 個檔案"
```

```tsx
<span>{t("files.uploadedCount", { count: uploadedCount })}</span>
```

如果所选语言缺少某个 key，格式化器会先尝试英文语言包，最后返回 key 本身。缺失 key 还会产生开发期警告，让不完整的翻译在开发过程中可见。

## 把服务端错误变成文案

有些失败由服务端或模型提供方产生，界面要做的不是复述它们，而是翻译**结构化的部分**、保留原文细节。规则只有一条：**按结构判断，绝不按英文措辞匹配**。

- 服务端给出的错误码：`cwd_missing` → `chat.cwdMissing`（提示挂载项目）、`chat.cwdNoticeMissing` / `…NotADirectory` / `…NotAllowed`。
- 提供方失败：`lib/provider-error.ts` 解析 `Error: <状态码> {json}`，得到 `kind`（`insufficient_balance`、`rate_limited`、`model_not_found` …），界面用 `chat.providerError.<kind>` 给出解释；无法识别的响应走 `chat.providerError.unknown` 并在参数里带上原文。
- **原始文本一律保留**：提供方响应的原始 JSON 放在卡片的「原始响应」折叠里，`request_id` 原样显示 —— 用户要靠它找提供方核对。
- 新增一种失败类别时，必须同时补齐 `en`、`zh-CN`、`zh-TW`。两条测试会守住这一点：`lib/i18n/registry.test.mjs`（三个语言包的 key 集合必须一致）与 `components/ProviderErrorCard.test.mjs`（每个 `kind` 都必须有译文）。

服务端返回的自由文本（例如 pi 的报错、提供方自己的 message、HTTP 状态描述）不翻译，只翻译它周围的界面框架文案。

## 验证

在仓库根目录执行：

```bash
node_modules/.bin/tsc --noEmit
npm run lint
npm test
```

日常开发不要运行 `next build`，原因见仓库的开发说明。

## 设计原则

Pi Web 是面向用户的网页界面，因此国际化是可用性与可访问性的一部分：人们应当能用自己熟悉的语言理解并操作界面。语言支持是为了降低使用门槛，而不是衡量技术水平的尺子，也不应成为排斥其它有价值贡献的理由。

i18n 层刻意是增量的：贡献者可以只新增一种语言，或只改进一小批界面文案，而不必改写 API 契约、改变 pi 的输出，或引入庞大的翻译框架。
