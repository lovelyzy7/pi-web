# 0007 — 第二因素与 API 令牌在代理之外，而不是塞进代理里

## 状态

已接受。

## 背景

账号与其会话已经入库（见 `docs/adr/0006-pi-web-database.md`），但对暴露在互联网上的服务器还差两件事：密码被偷就足以进入；脚本调用 API 的唯一方式是 HTTP Basic，也就是每个请求都发送口令。

双因素认证与 API 令牌都会与请求闸门交互，而闸门正是最容
易出错、代价又最高的地方：`proxy.ts` 会在每个请求上运行，包括 2.5 秒一次的运行状态轮询和每一帧 SSE。

## 决策

**TOTP 在账号页里登记、在登录时校验，代理从不检查它。**

- `lib/totp.ts` 用 `node:crypto` 实现 RFC 6238 —— 40 行，并用 RFC 自带的测试向量验证 —— 而不是为唯一必须正确的秘密引入依赖。真正值得引入依赖的是二维码这种展示层，它由 `qrcode` 生成。
- **登录变成两步**：`POST /api/web-auth` 带口令时返回 `{ok: false, totpRequired: true, challenge}` 且不下发 cookie；第二次 POST 带 `{challenge, code}` 才创建会话。挑战值以**已存储的口令哈希**作为 HMAC 密钥签名，因此改密码或 `session_epoch+1` 会让所有未用的挑战值立即失效，且无需额外数据表。
- 种子以 **AES-256-GCM** 加密，密钥文件独立（`~/.pi/agent/pi-web/secret.key`，0600），而不是存在数据库里：只拿到 `pi-web.db` 这一份文件 —— 操作者最可能备份或贴进 issue 的那份 —— 不足以生成有效的动态码。只恢复数据库而丢掉密钥时**失败关闭**并给出明确错误，因为静默拒绝正确的动态码与「验证器坏了」无法区分。
- 恢复码是单次使用的行，只存 **SHA-256 哈希**，账号页显示未使用数量，避免最后一个被不知不觉用掉。
- 一个动态码只能被接受一次：被接受的时间步写进 `account.totp_last_step`，等于或早于它的时间步一律拒绝。没有这一步，一个被瞥见的码在它 30 秒窗口内仍可再次登录。
- **一旦登记了第二因素，HTTP Basic 即被拒绝。**Basic 无法携带动态码，放行它会让登记变成装饰。401 会说明原因（`token_required`）并指向账号页。
- **API 令牌**（`Bearer pi_pat_…`）是替代方案。只存令牌的 SHA-256，明文只在创建时返回一次，`read` 令牌只能发安全方法，`last_used_at` 每分钟最多写一次，避免轮询客户端成为写入放大器。
- 两种机制都无法被枚举：未知、已撤销、已过期与错误的令牌在客户端看来都是不透明的拒绝，原因写进审计日志而不是响应体。

## 影响

- 开启第二因素会登出其它设备（它们的会话是在没有它的情况下创建的），并保留完成登记的那个浏览器。关闭同理：降级之后不应留下按更强策略授予的会话。
- 恢复码与动态码共享各自的限流 scope，因此错误动态码无法以错误口令的速度被磨掉。
- `/login` 是同一个页面的两种状态而非两条路由：挑战值只存在于内存里，刷新即从头开始，而不会留下一个半认证的页面。
- 安全响应头按需求拆分：固定不变的走 `next.config.ts` 覆盖所有路径；需要请求上下文的两者由代理施加 —— 基于 nonce 的 CSP 与 HSTS —— 因为只有代理知道请求是否真的走 HTTPS，也只有它能按响应生成 nonce。
- **CSP 默认是 `Content-Security-Policy-Report-Only`。**应用会注入一段内联主题脚本，Next 也会注入内联的 hydration 数据，因此差一条指令的强制策略会让升级后的安装直接坏掉。策略照常输出，浏览器控制台显示会被拦什么，等报告干净后用 `PI_WEB_CSP=enforce` 打开。
