# 0008 — 第三方主题是受作用域约束的 CSS，由服务端反代

## 状态

已接受。

## 背景

Pi Web 的外观是一组挂在 `[data-theme="…"]` 上的 CSS 变量（light、dark、mist、rose、pine），外加 `localStorage` 里的一个客户端偏好。它没有为「外观」留插件缝，所以想换配色的人只能改 `app/globals.css`。

CF-Server-Monitor 用另一种方式解决同一问题：第三方主题是来自 GitHub 仓库的完整 `index.html` + `assets/` 包，由 Worker 反代主题的 HTML 与资源，使浏览器从不接触 GitHub；管理后台则刻意保留内置主题。

那套设计无法照搬：Pi Web 是 React 应用，不是「每个请求渲染一页」，没有任何东西可以替换它的结构，而且它的 CSP（`style-src 'self'`）会拦掉任何其它源的样式表。真正值得借鉴的是它背后的机制：来源校验、同源代理、commit 与 branch 的差异化缓存策略，以及「坏主题碰不到能让操作者恢复的页面」这条边界。

## 决策

**Pi Web 主题是一份清单加一份只覆盖既定变量的样式表，由本服务提供，并作为内置配色之上的一层生效。**

- `theme.json` 声明身份、兼容性与 `base` 配色；`theme.css` 只能在 `html[data-pi-theme="custom"]` 作用域内覆盖既定变量。那个 `html` 前缀是关键：主题规则必须压过 `[data-theme="…"]` 配色块，且不依赖浏览器先加载哪份样式表。
- **主题没设置的变量仍由基础配色掌控。**服务端渲染 `data-theme="<manifest.base>"` 与 `data-pi-theme="custom"`，而内联初始化脚本与 `useTheme` 在主题生效期间都不会覆盖服务端的选择 —— 用户自己的配色选择仍被保存，并在移除主题后恢复。
- **主题由服务端取回并提供，绝不由浏览器直接获取。**这不只是 CORS 问题：在 `style-src 'self'` 之下，外部样式表会被直接拦掉；而代理副本可以被校验、限制大小、缓存在数据库里，并在断网时继续可用。
- **一切都在应用之前校验**：schema 与必填字段、每个选择器的作用域、禁止 `@import`、禁止外域 `url()`、禁止历史执行向量、体积上限、未知/保留变量警告，以及 WCAG 对比度检查。未通过的主题只被报告，不会被应用。
- **来源是 GitHub tree 地址、本地目录（`local:/…`），以及仅在 `PI_WEB_THEME_ALLOW_ANY_URL=1` 时开放的任意 HTTPS 地址。**回环与内网地址永远拒绝，因为代理不能被指向内网。本地目录必须位于可浏览的根目录或 `~/.pi/agent/themes` 之内 —— 后者是挂载的数据目录，也是文档里的放置位置 —— 或者由操作者在面板里显式批准（`allowLocal`），这与目录选择器批准一个项目是同一个决定。
- **主题永远到不了 `/login`、`/init` 与错误页。**代理在这些页面请求上标记 `x-pi-theme: off`，布局据此完全不渲染主题标记与样式表，镜像了 CF-Server-Monitor「管理后台保留内置主题」的边界：把一切藏起来的主题，不能连登录表单一起藏掉。
- **恢复手段在应用之外仍然可用。**`?theme=off`（以及主题分区里的按钮）会写一个服务端渲染时读取的 cookie，从而跳过主题而不是把它藏起来；样式表加载失败时守卫组件做同样的事。
- **按 commit 固定的来源按不可变缓存 24 小时，分支缓存一小时，本地目录每次请求都重新读取** —— 与 CF-Server-Monitor 相同的策略，也是 `local:` 主题在开发期间可用的原因。
- **资源按路径寻址**（`/api/themes/asset/theme.css`、`…/asset/assets/cursor.png`），这样样式表里的相对 `url(assets/…)` 才能正确解析；白名单接受 `theme.json`、`theme.css`、`theme.<模式>.css` 与 `assets/` 下的一切。
- **清单可以声明按模式拆分的变体**（`variants: { light, dark }`）。每个声明的变体都必须存在并通过与基础样式表相同的校验，否则整个主题被拒绝，而不是只在某一个模式下生效一半。服务端渲染 `base` 保证首屏正确，`ThemeVariantLink` 在模式切换时替换变体。
- **商店只是入口，不是授权。**商店清单里的每个条目都会被规范化成普通主题来源并重新校验，因此商店无法放行校验器本会拒绝的东西；商店清单与封面图同样由服务端取回并缓存。

## 影响

- 主题成为小而可审查的产物：一份清单加一份样式表。它不能执行代码、不能回连、也碰不到会让操作者陷入困境的页面。
- 变量列表成为公开契约。新增变量是加性的；重命名会破坏主题，因此 `docs/theme-development.md` 是参考文档，`lib/theme-manifest.ts` 保存机器可读的那份。
- **原本硬编码的颜色被提升为变量**（`--danger`、`--success`、`--warning`、`--info`、`--terminal-bg`、`--terminal-fg`、`--terminal-cursor`、`--qr-bg`）。没有这一步，主题只能给界面的一部分重新上色，而这正是先做它的原因。xterm 的调色板刻意保持字面值：xterm 在 JavaScript 里解析颜色，而且终端保留自己的配色也是惯例。
- 设置面板新增主题分区，配色选择器从「常规」迁到这里：外观只由一个地方决定。
- 分支每小时重新拉取，意味着主题可能在用户眼皮底下变化。界面会显示当前生效的引用，而发布 commit sha 是冻结它的文档化方式。
- 主题写入 `app_settings`（`theme:active`），因此对实例全局生效，而不是按浏览器。
